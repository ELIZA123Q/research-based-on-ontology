# 修复建议与优化交接

## 1. 隔离原则

评测过程负责说明“哪里不够、为什么不够、影响哪些题、需要什么证据”。后续执行过程负责判断是否新增、修改、降级、拒绝，以及如何写入完整本体。

本 Skill 不得：

- 直接输出 `ontology_bundle` 或 `optimized_ontology`。
- 直接创建 confirmed 对象、关系、状态变量、信号或资产影响。
- 把热点新闻、单篇研报观点、价格读数或短期公司动态写成稳定本体逻辑。
- 绕过材料和证据等级直接写入完整本体。

## 2. 修复建议分类

| 字段 | 用途 |
| --- | --- |
| `required_fixes` | 必须修复；否则不能发布或不能有条件发布 |
| `recommended_fixes` | 建议修复；影响质量但不一定阻断发布 |
| `backlog_items` | 后续版本规划或材料缺口 |
| `do_not_add_to_ontology` | 不建议纳入本体的内容 |

`required_fixes` 包括核心对象缺失、核心状态变量缺失、核心关系缺失、核心推理链断裂、关键验证信号缺失、严重本体不一致，以及核心业务结构图谱无法生成。

`recommended_fixes` 包括边界条件不足、反证能力较弱、结论表达不够清晰、中优先级环节覆盖不足和验证信号需要细化。

`backlog_items` 包括非核心扩展对象、少数问题才需要的关系、需要更多 reference 的逻辑和下一轮材料缺口方向。

`do_not_add_to_ontology` 包括单篇研报的一次性观点、某时点具体价格、公司短期新闻、无法复用细节、孤立实体和越界内容。

## 3. 本体膨胀控制

每条修复建议必须给出处理方式：

```text
add / update / split / merge / downgrade / deprecate / reject / supplement_evidence / defer / backlog
```

建议进入本体的内容应满足：

- 能支持多个投研问题。
- 代表稳定产业逻辑。
- 能参与推理链。
- 有可观察信号或验证方式。
- 能明显提升评测表现。

准入规则：

- 满足 4-5 条：可进入 `optimization_plan`。
- 满足 3 条：进入候选优化项。
- 满足 1-2 条：进入 backlog 或证据层。
- 完全不满足：进入 `do_not_add_to_ontology`。

## 4. `optimization_plan` 交接结构

评测失败或有条件通过时，可输出结构化计划项。每项必须先满足核心规范 `public_contracts.optimization_plan_item_minimum_contract`，再扩展评测来源字段：

```json
{
  "plan_id": "",
  "source_question_ids": [],
  "source_question_tier": "baseline/type_specific/hotspot/challenge",
  "source_issue_ids": [],
  "optimization_goal": "",
  "target_gaps": [],
  "target_file": "ontology_bundle_vN/05_reasoning.yaml",
  "target_path": "",
  "target_id": "",
  "legacy_path": "",
  "suggested_operations": [],
  "required_materials": [],
  "minimum_evidence_level": "single_source_candidate/multi_source_supported/official_source_supported/review_confirmed",
  "priority": "high/medium/low",
  "stop_condition": "",
  "quality_expected_delta": {
    "coverage_score": 0,
    "evidence_score": 0,
    "consistency_score": 0,
    "reasoning_score": 0
  }
}
```

`suggested_operations` 可使用：

```text
add split merge downgrade supplement_evidence revise_relation add_blocking_signal defer reject
```

所有 high 或 critical 失败题必须至少映射到一个 `optimization_plan` 或说明为什么进入 `do_not_add_to_ontology`。

图谱可生成性修复项必须在 `optimization_goal` 或 `target_gaps` 中写明缺失关系类型，例如 `segmentConnectsToSegment`、`companyRelatesToCompany`、`productRelatesToProduct`、`materialUsedInProduct`、`materialRelatesToMaterial`、`assetExposedToTarget`、`eventAffectsVariable`。`required_materials` 必须说明需要补充的端点验证材料、方向依据和关系语义属性。

## 5. 热点题修复规则

热点题触发的修复项必须标注：

- `source_question_tier=hotspot`
- `hotspot_source_refs`
- `minimum_evidence_level`
- `stability_assessment`

处理原则：

- 如果只是短期新闻事实，进入 `backlog_items` 或证据层。
- 如果新闻暴露了稳定传导链缺口，可进入 `recommended_fixes` 或 `required_fixes`，但必须要求多来源或官方来源验证。
- 如果热点事实无法核验，输出 `insufficient_reference_support`，不得作为 critical failure。
- 如果热点题暴露本体边界过窄，应建议补边界条件或目标范围说明，而不是盲目扩张对象。

## 6. 交接说明

`optimization_handoff` 可记录外部流程需要读取的交接内容：

```json
{
  "target_skill": "external_ontology_optimization_executor",
  "handoff_payload": ["evaluation_fix_report", "optimization_plan"],
  "execution_notes": [],
  "must_not_do": []
}
```

`must_not_do` 至少包含：

- 不要把评测建议直接升级为 confirmed。
- 不要把热点新闻直接沉淀为稳定产业逻辑。
- 不要补充与 `target_scope` 无关的对象。
- 不要输出买卖建议、目标价、收益率预测或仓位建议。
