# 投研本体人类可读解析输出要求

本文件定义如何把 `ontology_bundle_vN/` 转换为研究员可读的 `docs/ontology_guide.md`。本 Skill 只解释已有本体，不新增对象、关系、事实、假设、判断或结论。

## 1. 权威来源

| 内容 | 唯一来源 | 可辅助来源 |
|---|---|---|
| 概念、对象、关系、动作、推理、证据、治理 | `ontology_bundle_vN/` | `_compat/optimized_ontology_vN.json` 仅作回退 |
| 优化目标、批次、证据动作、变更原因、未解决问题 | `docs/production_notes.md` | `_artifacts/task_merge/*` |
| 来源材料、可靠性、使用限制 | `_artifacts/sources/source_material_summary.md` | `source_registry.json` |

过程文件只能解释背景，不能作为本体内容来源。若过程文件与 bundle 本体冲突，以 bundle 为准，并在报告中说明差异。

## 2. 输入形态

| 形态 | 输入 | 处理 |
|---|---|---|
| A | 只有 `ontology_bundle_vN/` | 生成基础解析，证据和变更说明标记为缺失。 |
| B | bundle + `docs/production_notes.md` | 解释优化目标和本体内容。 |
| C | bundle + 来源摘要 | 增强证据和来源说明。 |
| D | 完整 `release_package/` | 生成完整 9 章报告。 |

当前生产交付默认使用形态 D。

## 3. 报告结构

`docs/ontology_guide.md` 必须使用 9 章结构：

1. **阅读说明**：本体版本、权威数据、报告边界、推荐阅读顺序。
2. **一页概览**：研究主题、概念范围、对象规模、关系规模、状态分布、当前状态。
3. **这份本体能描述什么**：概念层、对象类型、关系类型、变量类型和当前使用情况。
4. **这个行业通常观察什么**：状态变量、传导模板、信号和情景路径。
5. **当前本体具体覆盖了什么**：行业、环节、公司、产品、材料、资产、事件、观测、假设、信号、判断。
6. **当前研究逻辑如何展开**：事件到变量、假设、信号、判断、资产影响的链路。
7. **哪些内容可信、哪些需要验证**：证据等级、候选状态、缺证项、不一致项、未解析项。
8. **研究员阅读提示**：使用边界、单一来源、候选内容、需人工关注事项。
9. **技术追溯附录**：ID 索引、JSON 路径、来源 ID、术语表和一致性检查。

章节可以根据空数据简化，但不能改变顺序。空章节要说明“本体未提供该类内容”，不得自行补齐。

## 4. 写作原则

- 先全局后细节，先说能用什么，再说不能用什么。
- 用研究员语言解释技术字段，同时保留 ID、关系类型和 JSON 路径。
- 把事实、假设、信号、判断、情景和资产线索分层写清。
- 对统计数值注明“机械统计，自动生成”。
- 不自动生成质量评分；质量评分属于评测 Skill。
- 不使用外部行业知识补全本体空白。
- 不为报告美观隐藏缺陷。

## 5. 统计规则

报告中的规模统计必须直接来自本体 bundle：

| 指标 | 统计口径 |
|---|---|
| 概念数 | `01_concepts.yaml` 按 `scopeStatus` 计数。 |
| 对象数 | `02_objects.yaml` 按类型计数。 |
| 关系数 | `03_relations.yaml` 按关系类型计数。 |
| 状态变量数 | `05_reasoning.yaml` 或 `02_objects.yaml` 中的 `StateVariable`。 |
| 传导链数 | `05_reasoning.yaml` 中的 `StateVariablePropagation` 或 `propagation_templates`。 |
| 来源数 | `06_evidence.yaml` 中的 `source_documents`。 |
| 证据主张数 | `06_evidence.yaml` 中的 `evidence_claims`。 |
| 候选/确认/废弃分布 | 按 `recordStatus` 或等价字段计数。 |

无法定位字段时，写“字段缺失，未统计”，不得估算。

## 6. 术语翻译

| 技术词 | 报告表达 |
|---|---|
| `Industry` | 行业/产业。 |
| `ConceptScheme` | 概念体系。 |
| `Concept` | 概念/术语。 |
| `ConceptBoundary` | 概念边界裁定。 |
| `Segment` | 产业链环节。 |
| `Company` | 公司。 |
| `Product` | 产品/技术路线。 |
| `Material` | 材料/投入品。 |
| `Asset` | 资产标的。 |
| `Event` | 事件。 |
| `StateVariable` | 需要持续观察的变量。 |
| `StateVariableObservation` | 某个变量在某个时间的观测。 |
| `StateVariablePropagation` | 变量之间的传导机制。 |
| `StateHypothesis` | 研究假设。 |
| `Signal` | 支持、跟踪、削弱或阻断信号。 |
| `JudgmentOutput` | 研究判断。 |
| `AssetImpact` | 资产影响线索。 |

翻译时保留原 ID，例如“先进封装需求（`VAR-012`）”。

## 7. 链路呈现

第 6 章应优先呈现 3-7 条核心链路。每条链路包含：

- 触发事件或起点变量。
- 中间变量和传导关系。
- 成立条件和时滞。
- 验证信号和反证信号。
- 可能影响的判断或资产线索。
- 证据来源 ID 或缺证说明。

如果链路断裂，应明确写“本体中缺少从 X 到 Y 的显式关系”，并记录缺失关系类型。

## 8. 缺陷暴露

以下情况必须在第 7 或第 8 章呈现：

| 缺陷 | 表达方式 |
|---|---|
| 空字段或缺关键口径 | “字段缺失，后续使用时需补充。” |
| 缺概念层或边界裁定 | “本体未说明范围和术语边界，使用时需先补概念层。” |
| 未连接对象或孤岛变量 | “本体中存在对象但没有进入可推理链路。” |
| 证据缺失或来源弱 | “只能作为候选线索，不能用于确认判断。” |
| 过程文件与本体冲突 | “过程说明与 JSON 不一致，以 JSON 为准。” |
| `provisional` / `candidate` 状态 | “候选内容，需后续证据确认。” |
| 资产影响链路跳跃 | “缺少判断到资产的中间证据或关系。” |

不得为了报告易读而删除这些提示。

## 9. 追溯附录

技术附录至少包含：

| 附录 | 内容 |
|---|---|
| ID 索引 | 关键对象、变量、关系、链路、来源 ID。 |
| Bundle 路径 | 重要结论对应的 `target_file`、`target_path`。 |
| 来源索引 | `source_id`、标题、发布主体、发布时间、可靠性。 |
| 术语表 | 技术字段到中文表达的映射。 |
| 一致性检查 | 统计数、孤岛项、缺证项、冲突项。 |

附录可以折叠，但不能省略追溯信息。

## 10. 输出质量门槛

| 检查项 | 通过标准 |
|---|---|
| 忠实 | 报告内容均可回到本体 JSON 或过程文件。 |
| 可读 | 非技术读者能理解范围、逻辑和限制。 |
| 可追溯 | 关键对象、链路和证据保留 ID 或 JSON 路径。 |
| 不美化 | 缺失、候选、弱证据和冲突被明确暴露。 |
| 不越权 | 不做质量评分、发布判断或投资建议。 |

## 11. 禁止事项

- 不新增本体不存在的对象、关系、变量、事实、假设、判断或资产结论。
- 不使用外部行业知识补全本体。
- 不把前置材料包中的逻辑当作已入库内容。
- 不修改 `ontology_bundle_vN/` 或 `_compat/optimized_ontology_vN.json`。
- 不判断是否发布。
- 不输出买卖建议、目标价、收益率预测或仓位建议。
