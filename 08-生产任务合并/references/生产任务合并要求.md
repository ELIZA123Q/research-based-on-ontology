# 生产任务合并要求

本文件定义如何把缺口发现、历史回放、评测缺陷、推理反馈和用户修订请求合并为本体优化 Skill 可执行的 bundle 路径化任务单和 patch request queue。本 Skill 只编排任务，不修改本体，不执行补证，不判断发布。

## 1. 输入来源

| 来源 | 典型文件 | 处理 |
|---|---|---|
| 缺口发现 | 缺口报告、交接块、gap_items、candidate_patch_requests | 提取缺口类型、建议动作、证据要求、evidence ids 和预期收益。 |
| 历史回放 | 回放报告、case_replays、validation_recommendations、temporal_replay_evidence、invalidation_candidates | 提取失败案例、诊断项、建议动作、受影响组件和失效候选。 |
| 评测 | evaluation_report、defect_tickets、optimization_plan | 提取失败题、维度弱项、发布阻断和修复建议。 |
| 推理反馈 | ontology_feedback、reasoning_result、inference_run | 提取弱命中、断链、误触发、漏触发、缺证项和 candidate patch request。 |
| 用户修订 | user_revision_request | 提取明确要求、范围限制和人工优先级。 |
| 材料搜索 | source_quality_assessment、source_registry | 只用于判断补证可行性，不直接生成结构改动。 |

没有任何诊断来源时，不生成任务单，只说明缺少输入。

## 2. 归一化映射

不同来源统一映射为优化任务项。

| 来源字段 | 目标字段 |
|---|---|
| `gap_id`、`finding_id`、`defect_id`、`request_id` | `source_ids` |
| 缺口类型、诊断类型、失败维度 | `issue_type` |
| 建议动作、修复提示、用户要求 | `suggested_operations` |
| 受影响对象、变量、关系、题目、案例 | `target_components` |
| 材料要求、证据缺口、数据需求 | `required_materials` |
| 严重度、发布阻断、用户优先级 | `priority_inputs` |
| 停止条件、拒绝条件、边界说明 | `stop_condition` 与 `scope_boundary` |
| `evidence_episode_ids`、`evidence_claim_ids`、`invalidation_candidate_ids` | `evidence_episode_ids`、`evidence_claim_ids`、`invalidation_candidate_ids` |

## 3. 任务项结构

`optimization_task_items.json` 是数组。每项至少包含：

| 字段 | 要求 |
|---|---|
| `task_id` | 稳定 ID，如 `OPT-TASK-001`。 |
| `task_title` | 具体可执行，避免“完善”“优化”等空词。 |
| `issue_type` | 缺口、回放失败、评测缺陷、用户修订、补证等。 |
| `source_ids` | 溯源到原始缺口、案例、题目或请求。 |
| `target_components` | 目标对象、关系、变量、信号或范围。 |
| `target_file` | 建议写入或检查的 bundle 文件，如 `ontology_bundle_vN/05_reasoning.yaml`。 |
| `target_path` | bundle 内部路径，如 `state_variables[SV-001]`。 |
| `target_id` | 目标对象、关系、变量、信号、证据或治理项 ID。 |
| `legacy_path` | 旧 JSON 路径，可选，如 `optimized_ontology.state_variables`。 |
| `optimization_goal` | 本轮要达成的具体结果。 |
| `suggested_operations` | add/update/strengthen/split/merge/downgrade/deprecate/reject/supplement_evidence 等。 |
| `required_materials` | 材料类型、最低证据等级和来源要求。 |
| `expected_change` | 应产生的结构变化或质量改善。 |
| `expected_benefit` | 提升 coverage/evidence/consistency/reasoning 的哪一项。 |
| `risk_if_ignored` | 不处理的影响。 |
| `priority` | P0/P1/P2/P3。 |
| `stop_condition` | 何时停止扩张或判定无法处理。 |
| `evidence_episode_ids` | 支撑该任务的 EvidenceEpisode ID，可为空但需说明原因。 |
| `evidence_claim_ids` | 支撑该任务的 EvidenceClaim ID，可为空但需说明原因。 |
| `invalidation_candidate_ids` | 若任务来自历史回放或推理失效，记录相关失效候选 ID。 |
| `semantic_risk` | low/medium/high/core_change_required。 |
| `merge_precondition` | 进入优化 Skill 合并前必须满足的证据、审核或核心规范条件。 |

## 3.1 patch_request_queue.yaml

`patch_request_queue.yaml` 是面向优化 Skill 的候选补丁队列。每项至少包含：

```yaml
- patch_request_id: PRQ-YYYYMMDD-001
  source_task_ids: []
  source_ids: []
  evidence_episode_ids: []
  evidence_claim_ids: []
  invalidation_candidate_ids: []
  target_file: 05_reasoning.yaml
  target_path: ""
  target_id: ""
  operation: add
  semantic_risk: medium
  priority: P1
  merge_precondition: ""
  review_requirement: ""
  queue_status: pending
```

规则：

- queue 中的事项不代表正式改动。
- `queue_status` 只能是 pending、deferred、rejected、blocked_by_core_change；merged 只能由优化 Skill 写入 patch ledger。
- 缺少 evidence ids 的高风险任务必须标记 `merge_precondition`，不能直接合并。

## 4. 去重规则

合并任务时先按目标和意图去重，不按文字相似度简单去重。

同一任务需要同时满足：

- 目标组件相同或高度重叠。
- 修复目标相同。
- 所需材料相同或可共享。
- 预期结构变化相同。

若来源不同但互相强化，合并为一项，并保留全部 `source_ids`。若目标相同但方向冲突，保留为冲突任务，进入 `priority_decision.md`。

## 5. 优先级

默认按四维排序：

| 维度 | 高优先级信号 |
|---|---|
| 影响程度 | 阻断核心推理、发布失败、关键链路断裂、严重误触发/漏触发。 |
| 证据可得性 | 已有高可靠材料或可短期补证。 |
| 结构收益 | 能显著提升覆盖、证据、一致性或推理能力。 |
| 风险控制 | 不处理会导致错误结论、资产跳跃、合规风险或图谱不可生成。 |

优先级含义：

| 优先级 | 处理 |
|---|---|
| P0 | 本轮必须处理，否则本体不可用于目标范围。 |
| P1 | 建议本轮处理，显著提升可用性。 |
| P2 | 可延后处理，需要更多材料或影响较窄。 |
| P3 | 低价值、低证据或仅作观察，默认不进入本轮优化。 |

## 6. 补证回路

缺少材料但任务重要时，生成补证任务而不是直接结构修改。

补证任务必须写明：

- 需要什么材料。
- 最低证据等级。
- 可接受来源类型。
- 失败后如何处理。
- 最多补证轮次。

连续两轮仍无法获得最低材料时，任务降级为 `defer` 或 `reject`，不得无限循环。

## 7. 拒绝和延后

以下情况默认拒绝或延后：

- 超出当前本体范围。
- 只能由目标价、评级、推荐语、收益率预测或仓位表达支持。
- 无来源、来源低可靠且无法回溯原文。
- 预期收益不明确，不能提升四项质量分。
- 需要核心 schema 变更但缺少跨场景必要性。
- 会引入投资建议或交易指令风险。

拒绝项必须保留来源、拒绝原因和可能重新考虑的条件。

## 8. 输出文件

### `optimization_task_list.md`

面向人读，按 P0-P3 分组。每项包括：任务标题、来源、为什么重要、建议动作、所需材料、预期收益、风险和停止条件。

### `optimization_task_items.json`

面向优化 Skill，包含第 3 节任务项结构。字段必须可机器解析，不用 Markdown 包裹。

### `patch_request_queue.yaml`

面向优化 Skill，包含第 3.1 节 patch request queue 结构。该文件是 PatchLedger 的输入，不是 PatchLedger 本身。

### `priority_decision.md`

说明排序依据、合并逻辑、冲突任务、拒绝项、延后项和补证任务。必须解释为什么 P0 进入本轮，为什么某些看似重要的任务被延后。

## 9. 质量门槛

| 检查项 | 通过标准 |
|---|---|
| 可执行 | 每项有目标、动作、材料和停止条件。 |
| 可追溯 | 每项能回到原始诊断或用户请求。 |
| 不重复 | 同目标同意图任务已合并。 |
| 不膨胀 | 低价值、低证据、越界任务被拒绝或延后。 |
| 可交接 | JSON 任务项能直接进入优化 Skill。 |
| Patch 队列 | 可执行结构改动进入 patch_request_queue，并保留 evidence ids、目标路径和 merge_precondition。 |

## 10. 禁止事项

- 不修改本体，不输出 `ontology_bundle_vN/` 或 `optimized_ontology_vN.json`。
- 不把缺少证据的任务标记为已完成。
- 不输出发布结论。
- 不用“优化”“完善”“补充”等模糊词替代具体 `expected_change`。
- 不为拒绝项写空洞理由。
- 不把 patch_request_queue 的 pending 项写成已合并；合并、拒绝、延后和失败由优化 Skill 追加 patch ledger。
