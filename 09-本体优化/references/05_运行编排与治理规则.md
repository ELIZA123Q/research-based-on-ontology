# 运行编排与治理规则

本文定义优化 Skill 的运行模式、patch 合并、patch ledger、缺口分批、核心适配和核心规范变更分流。本文只描述要求和结果，不描述执行过程细节。

## 1. 运行模式

| 模式 | 要求 |
|---|---|
| `auto_batches` | 默认模式。一次任务可连续处理多批缺口。每批最多 1-3 个同主题簇缺口。 |
| `single_batch` | 只处理当前最高优先级批次。 |
| `full_rebuild_review` | 用于缺口过多、结构接近重构或核心债务过重的场景。输出完整本体、重构建议和核心规范变更建议。 |

任何模式都必须保留证据追踪、改动预算、稳定性审计、核心适配审查和核心变更分流。

## 2. 输出模式

| 模式 | 批次内部 | 最终交付 |
|---|---|---|
| `patch` | 输出 `optimization_delta`。 | 自动合并后的完整 `optimized_ontology`。 |
| `full` | 输出完整 `optimized_ontology`。 | 完整 `optimized_ontology`。 |

`patch` 不是最终交付物。最终 JSON 不得把未合并 `optimization_delta` 作为权威结果。

`full` 适用于以下情况：

- 输入本体无版本号、无 `base_hash` 或为初版草稿。
- 连续 patch 批次达到 5 批。
- P0 缺口全部解决。
- 最近 2 次稳定性审计为 `warning` 或任一次为 `fail`。
- `ontology_scope.scope_type`、容器级元数据或跨 3 个以上主题簇同步变化。
- 单批预计新增或废弃对象超过 20 个。
- patch 合并、schema 校验或稳定性审计失败。

## 3. patch 契约

`optimization_delta` 必须包含 `delta_metadata`、`delta_summary` 和 `delta_changes`。当存在 `_artifacts/task_merge/patch_request_queue.yaml` 时，本轮 delta 必须能回溯到一个或多个 PatchRequest。

`delta_metadata` 至少包含：

- `base_ontology_version`
- `base_hash`
- `batch_id`
- `round_number`
- `generated_at`
- `source_patch_request_ids`

`delta_changes` 使用以下规则：

- `added_*` 写完整对象或关系。
- `updated_*` 只写实际变化字段。
- `deprecated_*` 和 `rejected_*` 写目标 ID、原因、证据引用和动作。
- 核心 schema 不存在的类型、字段或枚举不得写入 delta。
- 每项变更尽量记录 `evidence_episode_ids`、`evidence_claim_ids`、`target_file`、`target_path` 和 `target_id`。

每个 patch 批次合并后必须生成完整 `optimized_ontology` 或 `ontology_bundle_vN/`，并把批次状态写入 `optimization_run_log.batches[*]`。合并、拒绝、延后或失败都必须追加 `PatchLedgerItem`。

## 3.1 patch_request_queue 输入

`patch_request_queue.yaml` 是 6-4 生成的候选补丁队列。每项至少包含：

- `patch_request_id`
- `source_task_ids`
- `source_ids`
- `evidence_episode_ids`
- `evidence_claim_ids`
- `invalidation_candidate_ids`
- `target_file`
- `target_path`
- `target_id`
- `operation`
- `semantic_risk`
- `priority`
- `merge_precondition`
- `review_requirement`
- `queue_status`

处理规则：

- `queue_status=pending` 才能进入本轮合并评估。
- `semantic_risk=core_change_required` 必须进入核心规范变更分流，不得硬凑实例改动。
- 缺少 evidence ids 且风险为 high/core_change_required 的请求不得合并，只能补证、延后或拒绝。
- 任何 queue 项被合并、拒绝、延后或失败，都必须写入 `patch_ledger.yaml`。

## 3.2 Patch Ledger 输出

`_artifacts/patches/patch_ledger.yaml` 是 append-only 账本。每项至少包含：

```yaml
- patch_id: PLI-YYYYMMDD-001
  patch_request_id: PRQ-YYYYMMDD-001
  base_ontology_version: ""
  base_hash: ""
  operation: add
  merge_status: merged
  merged_at: ""
  target_file: 05_reasoning.yaml
  target_path: ""
  target_id: ""
  evidence_episode_ids: []
  evidence_claim_ids: []
  merge_reason: ""
  semantic_risk: medium
  reviewer_requirement: ""
```

规则：

- patch ledger 创建后不可修改；修正只能追加新账本项。
- `merge_status` 使用 `merged`、`rejected`、`deferred`、`failed`。
- `rejected_patch_requests.yaml` 必须保留拒绝原因和重新考虑条件。
- `patch_merge_report.md` 面向人读，说明本轮合并证据、风险、影响模块和未处理事项。

## 4. 缺口分级

每个缺口按三类维度记录：

| 维度 | 取值 |
|---|---|
| `blocking_level` | `P0`、`P1`、`P2` |
| `dependency` | `independent`、`depends_on[gap_id]`、`blocked_by_core_change` |
| `expected_change_scope` | `small`、`medium`、`large` |

P0 阻断关键推理链。P1 显著影响推理质量。P2 提升完备性。

`large` 缺口不得整体进入单批，必须拆成子缺口。

## 5. gap_buckets

`optimization_report.gap_buckets` 必须包含以下桶：

- `P0_independent`
- `P0_blocked`
- `P1_independent`
- `P1_blocked`
- `P2_deferred`
- `core_change_blocked`
- `resolved`

每个 gap 至少包含：

- `gap_id`
- `gap_type`
- `gap_description`
- `blocking_level`
- `dependency`
- `expected_change_scope`
- `source`
- `target_structures`
- `affected_chain_ids`
- `suggested_playbook`
- `topic_cluster_id`
- `status`

`core_change_blocked` 中的 gap 必须在独立 `core_change_proposals` 文件中有对应 proposal。

## 6. 批次选择

批次选择顺序如下：

```text
P0_independent
→ P0_blocked 中依赖已解除者
→ P1_independent
→ P1_blocked 中依赖已解除者
→ P2_deferred（仅里程碑 full 审计时评估）
```

同批缺口必须属于同一主题簇。主题簇可以由同一 `industry_segment`、同一 `affected_chain_ids`、同一组核心状态变量、同一 `suggested_playbook` 或同一 large 缺口的子缺口确定。

`optimization_report.batch_selection` 必须记录：

- `batch_id`
- `selected_gap_ids`
- `selection_bucket`
- `topic_cluster_id`
- `selection_reason`
- `deferred_gap_ids`
- `blocked_gap_ids`
- `core_change_blocked_gap_ids`
- `expected_change_scope`
- `change_budget_hint`

## 7. 停止条件

满足任一条件即停止自动批处理：

- P0 缺口全部解决。
- P0+P1 剩余数量 ≤ 5。
- 连续 3 批无实质 `add/update`。
- 最近 3 批中 ≥ 80% 证据为 `no_evidence`。
- 合并、schema 校验或稳定性审计失败。
- 用户指定 `stop_condition=manual`。
- 所有剩余 P0/P1 均依赖核心规范评审。

停止原因写入 `optimization_run_log.stop_reason` 和 `next_optimization_plan`。

## 8. 核心适配审查

每个重大结构改动必须归入一类：

| 分类 | 实例处理 | proposal 要求 |
|---|---|---|
| `instance_fit` | 正常改实例。 | 不需要 proposal。 |
| `instance_workaround_with_core_debt` | 可做候选级临时实例改动。 | 必须生成 proposal，并记录 `core_change_proposal_id`、临时目标和迁移方式。 |
| `core_required` | 禁止实例改动。相关 gap 进入 `core_change_blocked`。 | 必须生成 proposal。 |

`core_required` 不得通过泛化对象、泛化关系、描述字段或 `reviewNote` 硬凑成已解决实例改动。

## 9. 核心规范变更分流

以下建议必须进入核心变更分流：

- 新增、删除或修改对象类型。
- 新增、删除或修改关系类型、端点类型、方向或关系属性。
- 新增、删除或修改动作类型、状态机、权限或审计规则。
- 新增、删除或修改公共枚举值。
- 新增、删除或修改核心公共字段或容器级元数据。
- 修改 `public_contracts` 或跨 Skill 最小契约。
- 现有 schema 无法表达且可能具备跨行业复用价值。

本 Skill 不直接修改 `../../spec/投研本体核心规范/*`。核心规范变更建议必须单独输出 JSON 文件：

```text
outputs/core_change_proposals/{ontology_id}_{run_id}_core_change_proposals.json
```

没有核心变更建议时，也输出合法空文件。

## 10. core_change_proposals 文件

每条 proposal 至少包含：

- `proposal_id`
- `trigger_batch_id`
- `source_gap_ids`
- `original_suggestion`
- `proposal_type`
- `core_files_or_sections`
- `affected_schema_elements`
- `why_existing_schema_is_insufficient`
- `suggested_core_change`
- `impact_assessment`
- `evidence_refs`
- `risk_level`
- `suggested_reviewer_role`
- `not_applied_reason`
- `downstream_handling`

`optimization_report.core_change_proposals_file.sha256` 必须与独立文件内容一致。

## 11. run log

`optimization_run_log` 至少记录：

- `run_id`
- `run_mode`
- `started_from_version`
- `final_version`
- `batches`
- `final_delivery_status`
- `stop_reason`
- `core_change_proposals_file`

每个批次至少记录：

- `batch_id`
- `selected_gap_ids`
- `optimization_mode`
- `delta_change_count`
- `merge_status`
- `validation_status`
- `core_change_proposal_count`
- `notes`
