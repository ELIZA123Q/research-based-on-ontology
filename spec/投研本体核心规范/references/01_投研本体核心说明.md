# 01-投研本体核心说明

本文件回答三个问题：为什么要建投研本体、这套本体由什么构成、如何保证它长期可用。

本目录采用"MD 解释 + YAML 约束"的结构：本文件讲原理与治理；《02-投研本体建模规格说明》讲概念、对象、关系、动作的建模方法；`schema/objects.yaml`、`schema/relations.yaml`、`schema/actions.yaml` 是给 AI、前端和后端读取的正式机器规范；行业实例负责把具体概念和业务对象跑通。

---

## 一、建设目标与价值

### 1.1 现状问题：判断散落，无法复核、复盘和复用

投研工作中每天都有大量判断产生：某家公司毛利率可能改善，某个行业需求可能复苏，某类产业线索还没被市场充分定价，某个风险可能推翻原来的逻辑。这些判断如果只停留在研报、会议纪要或个人经验里，就会带来三个问题。

**看不清依据**：别人只能看到结论，看不清这个判断说的是哪个对象、当时的证据是什么、在什么时间成立。

**无法复核**：判断升级时，无法检查是否有足够信号支持、是否遗漏了关键反证、市场是否已经充分定价。

**无法复盘**：事后想回看一个判断为什么对或错，却找不到当时的完整逻辑，无法区分是推理本身有问题、还是外部条件变了。

### 1.2 本体的作用

投研本体的核心作用，是把每一条投研判断挂到具体业务对象上，并记录它的证据、信号、判断状态和后续修正。

由此形成一张投研知识网络：概念层先定义研究范围和术语口径，业务对象是骨架，判断附着在对象上，证据和信号说明判断为什么成立、为什么变化。每一条判断最终都能回答四个问题：这个词和范围是什么意思、说的是哪个对象、依据哪些证据、在什么时间和条件下成立。

判断录入支持多种起点：可以从事件出发，也可以从状态变化、信号、已有结论或风险暴露进入，再逐步补全可追溯链条。

### 1.3 长期沉淀的成果

判断持续录入并经过复盘校准之后，公司积累的不只是一堆研报，而是六类可持续复用的知识资产。

**事件原型**：同类事件通常如何影响行业、公司和资产，形成可套用的分析框架。

**状态变量库**：某个行业或公司研究中长期关注的关键状态维度，减少每次重复定义的成本。

**判断逻辑**：状态变化如何传导到资产影响，哪些传导路径历史上反复有效。

**验证信号库**：哪些数据、事实或观察可以验证判断，不同信号的可靠性和时效性如何。

**削弱与阻断经验**：哪些条件会削弱、阻断或限制判断，常见误判的触发原因是什么。

**复盘记录**：历史判断是否兑现，哪些逻辑有效，哪些假设失效，失效原因是什么。

这六类知识资产并非独立存在，而是通过本体的概念和对象结构承载和沉淀：行业范围、术语和边界沉淀在 ConceptScheme、Concept 和 ConceptBoundary 中；事件原型沉淀在 Event 和 StateVariablePropagation 中；状态变量库和判断逻辑沉淀在 StateVariable、StateHypothesis 及其传导关系中；验证信号库沉淀在 Signal 对象及其可信度与历史验证字段中；削弱与阻断经验沉淀在 blocking / weakening 信号的阻断依据和 ActionAudit 中；复盘记录沉淀在 ReviewRecord 的四个复盘维度中。第二章将对这些对象逐一定义。

### 1.4 本体的边界

明确边界，有助于建立对本体的准确预期。

**辅助判断，不替代判断**：行业理解、公司认知、信号强弱、阻断依据是否成立，仍需研究员或授权角色确认。本体整理判断结构，判断本身由人完成。

**定义结构，不负责数据接入**：公告、研报、财报、调研纪要等原始数据，通过数据管道接入后映射为本体对象。本体负责定义结构，数据清洗由数据管道承担。

**定义概念层，不替代行业百科**：核心规范只规定概念层如何表达范围、术语、边界和来源追溯，不把半导体、医药、新能源等行业的具体概念写死在核心规范中。具体行业概念应进入对应本体实例，并绑定权威来源。

**支持规则校验，不自动推理**：当前阶段的重点是定义对象、关系、动作和审核口径。后续可逐步增加规则校验和智能体能力；投资判断由研究员做出，系统不自动生成。

**个人草稿留在应用层**：个人笔记、临时观点和个人偏好留在应用层。经过复用和审核的内容，方可进入行业扩展层或本体层。

**表达研究判断，不生成交易指令**：资产影响表达研究判断对资产的预期影响，不等于建仓建议、仓位决策或交易指令。

### 1.5 本体版本与质量

投研本体工程体系的长期资产不是某一次任务输出，而是持续迭代的 `optimized_ontology`。因此每份 `base_ontology`、`optimized_ontology` 或多本体包都应携带容器级 `ontology_metadata`，用于追踪版本来源、父版本和质量变化。

`ontology_metadata` 至少包含 `ontology_id`、`ontology_version`、`parent_version`、`created_by`、`updated_by`、`change_reason` 和 `ontology_quality`。其中 `ontology_quality` 使用六个 0-1 分值，分别衡量覆盖、证据、时间证据、补丁审计、一致性和推理可用性：

- `coverage_score`：研究范围内对象、变量、关系、信号、情景和资产映射是否足够。
- `evidence_score`：来源、事实观测、证据等级和可追溯性是否充分。
- `temporal_evidence_score`：EvidenceEpisode、EvidenceClaim、有效期、失效记录和当前有效证据过滤是否充分。
- `patch_audit_score`：PatchRequest、PatchLedgerItem、合并/拒绝原因和版本演化审计是否充分。
- `consistency_score`：schema 合法性、关系端点、重复、冲突和状态一致性是否合格。
- `reasoning_score`：是否支持链路推理、反证、情景路径和资产线索表达。

完整字段定义、取值范围与检查重点见 `schemas/ontology_bundle.yaml` 中的 `ontology_container_metadata.ontology_quality`。

版本升级不等于对象数量增加。一次优化只有在覆盖能力、证据质量、一致性或推理能力提升时，才应被视为质量改善；如果只是把低质量候选堆入本体，应在质量检查和缺口计划中暴露。

## 二、本体结构

### 2.1 推理主线

本体的核心，是把投研推理过程结构化。不同事件进入系统的方式不同，但进入后走的是同一套推理结构。

**触发研究的事件常见来源**包括：财报或公告中的数据异常、资产价格异动、产业链调研反馈、宏观政策变化、市场主题出现或退潮、研究员主动发起的专题研究。来源不同，但都落成同一种对象——事件（Event），然后进入推理主线。

**主传导链**如下：

```
事件（Event）
  → 影响业务对象上的状态变量
  → 状态变量之间发生传导
  → 形成状态假设（研究员的方向性判断）
  → 形成判断输出
  → 产生资产影响，作用于资产标的
```

这条主线揭示了一件重要的事：事件本身不直接形成资产重估。真正驱动资产判断的，是事件引发的状态变量变化，以及研究员对这些变化的假设判断和信号验证。

主线中需要区分两个层次：**主传导链**是判断从事件到资产影响的核心路径；**信号层**是支持、催化、跟踪或削弱主链的证据，包括支持与跟踪信号（validation/tracking）、催化信号（catalyst）和削弱信号（weakening/blocking），用于说明主链中某个状态变化或判断逻辑凭什么成立、何时可能被市场触发，以及在什么条件下被削弱或阻断。

```
信号层（支持/跟踪）：validation/tracking 信号 → 支持或跟踪状态假设、判断输出
信号层（催化）：catalyst 信号 → 催化判断输出（不直接作用于状态假设）
信号层（削弱）：weakening 信号 → 削弱状态假设或判断输出
             blocking 信号 → 阻断状态假设（不直接作用于判断输出）
```

信号不是推理链的下一步，而是对主链的支撑和约束。

本体还允许**反向结构化**：分析师实际工作中常常先形成初步判断，再组织证据。本体支持从已有判断或资产影响出发倒推，逐步补全事件、状态变量和信号。反向结构化是一种录入方式，不是证明方式——最终判断是否有效，仍取决于能否补全完整链条。

本体主干仍采用 Palantir 式对象、关系、动作和状态机。Graphiti 式 temporal context graph 的启发只进入证据和运行记录层：每次材料、历史案例、推理反馈或评测反馈先形成 EvidenceEpisode，再抽取 EvidenceClaim / EvidenceFact，最后通过 PatchRequest 和本体优化 Skill 决定是否进入正式主干。Evidence Graph 不能绕过优化 Skill 直接修改 `01_concepts.yaml` 到 `05_reasoning.yaml`。

《02》对主线中每个节点的建模方法做解释说明；正式对象定义、关系规格和动作规则以 `schema/` 下的 YAML 为准。

### 2.2 对象

本体里的对象分为五类，各层典型对象和建模规则详见《02》§3，正式字段定义见 `schemas/objects.yaml`。此处仅概述各层核心职责：

| 层级 | 核心职责 | 详见 |
|---|---|---|
| 概念定义层 | 定义研究范围、术语口径、同义词、边界裁定和概念到业务对象的映射。回答"讨论什么、边界在哪、术语怎么归一" | 02 §3、02 §4 |
| 研究标的层 | 提供现实世界锚点（产业、环节、公司、产品、材料、资产）。判断和资产影响须挂到这一层 | 02 §3 |
| 可观测维度层 | 表达对象状态及其变化。变量是"观察什么口径"，观测是"某时点看到什么事实"，两者严格区分，不得混用 | 02 §3、02 §4 |
| 研究推理层 | 表达从事件→假设→信号→判断→资产影响的完整推理过程。判断生命周期包括候选、观察中、有效、正式触发、已验证、已过期、已定价、已废弃 | 02 §3、02 §4、02 §6 |
| 来源与记录层 | 支撑来源追溯、证据摄入、动作留痕、审核和复盘。这些对象支撑主干，但不替代主干 | 02 §3、02 §4、02 §6 |

### 2.3 关系

本体里的对象不能只靠文字描述关联，必须通过显式关系连接。概念上位下位、产业链连接、变量挂载、假设-信号-判断的支撑/削弱/阻断、来源追溯等，不能只写在报告段落里或用 `positionInChain` 暗示。关系显式化之后，系统才能支持有意义的查询和复盘。

关系分类、常用关系速查、建模规则详见《02》§5；正式关系端点、基数、属性和机器校验规则见 `schemas/relations.yaml`。

### 2.4 动作

本体不是静态图谱，还要记录谁做了什么操作。提出状态假设、添加信号、升级或降级判断、废弃一条路径，都必须通过标准动作完成，不能随意编辑字段。动作审计（发生了什么操作）与审核记录（是否被认可）是两件不同的事。

动作分类、常用动作速查、状态机生命周期详见《02》§7；正式动作规格、前置条件、状态流转和审计策略见 `schemas/actions.yaml`。

### 2.5 时间

投研判断天然有时间属性。一个判断上周成立，不代表这周仍成立；一条信号刚出现时很强，过了观察窗口可能就失效。

本体区分两类时间：

| 时间类型 | 含义 |
|---|---|
| 业务时间 | 事实、信号或判断在现实中何时发生、何时有效 |
| 系统时间 | 系统何时记录或修正这条信息 |

区分这两类时间对复盘至关重要。一条削弱信号可能 3 月 1 日已经出现，但研究员 3 月 15 日才录入系统。复盘时必须知道：现实中信号何时出现，系统当时是否已经知道。完整时间字段规格见《02》第二章各对象属性说明。

Temporal Evidence Layer（证据时间层）的具体规则——包括 `validFrom`/`validTo`、失效标记与替代、历史回放读取策略、EvidenceClaim 时间字段等——详见《03》§7。

## 三、本体治理

治理回答三个问题：谁有权改什么、什么内容能进本体层、进入之后如何保持健康。

### 3.1 三层权限边界

本体采用三层结构划定写入权限和影响范围。这三层不是内容分类，而是每一层的内容由谁负责、改动影响谁。

**本体层**：全公司共享，所有人可见、可引用，但只有本体维护方有权修改。包含业务对象骨架、判断结构的通用定义、核心关系类型和核心动作类型。新增、修改、降级和废弃均需评审。一旦改动，影响全公司所有使用者，因此本体层应保守扩张。

**行业扩展层**：特定行业的共享内容，本行业研究员可见、可引用，由行业负责人或行业首席负责维护。通过行业标签、状态变量模板、事件模板和判断模板来承接行业差异，不另建一套孤立本体。内容应服务于本行业多个研究员，而不是某个人的个人习惯。

**应用层**：个人工作空间，只有本人可见和修改。包括个人视图、研究草稿、个人收藏和复盘笔记。应用层内容可以引用本体对象，但不得直接改变本体结构。当不确定某个内容属于哪一层时，默认放入应用层。

判断某项内容应放在哪一层，可参考以下标准：多个行业都需要、且属于判断表达的基础结构，进入本体层；某一行业长期使用、但不具备跨行业通用性，进入行业扩展层；某位研究员或团队在复盘中形成的偏好或经验，放入应用层。

### 3.2 入库标准

以下五条是内容进入本体层的基本条件。完整规格见《02》。

**1. 判断须有锚点**：每条判断须能追溯到具体业务对象。"看好新能源"这类没有明确公司、产业、产品或资产的表述不符合入库标准。市场主题类判断须先落到具体业务对象、行业标签或投资命题上，再进入本体层。

**2. 判断须有证据**：状态假设和判断输出须关联事件、状态变量或支持信号。仅有结论（如"公司基本面改善"）而无证据支撑，不符合入库标准。

**3. 削弱和阻断信号须有作用对象**：每条削弱或阻断信号须明确指向它所作用的状态假设或判断。仅写"行业竞争加剧"而不说明它削弱或阻断哪条假设，不符合入库标准。

**4. 时间须可追溯**：信号、判断和修正须有时间锚点，包括观测时间、来源时间和适用窗口。"调研反馈订单不错"若无时间信息，不符合入库标准。

**5. 关键变更须有动作审计**：判断升级、降级、阻断、废弃须通过标准动作完成，并记录执行人、执行时间、前后状态和操作依据。直接修改判断等级而不留动作记录，不符合入库标准。

### 3.3 长期维护

本体不是建完就不变的系统，需要随着使用持续调整。长期维护包含三个方向。

**向上沉淀**：应用层或行业扩展层中，被多人、多次、稳定复用的内容，可以申请升级为上一层资产。升级前需回答四个问题：该内容是否具有跨行业通用性；是否无法用现有对象或关系表达；升级后是否影响已有结构；是否有清晰定义和明确的禁止用法。

**向下降级或废弃**：本体层并非只增不减。长期无人使用、填充率低、只被单一行业使用、与已有结构重复、维护成本高于使用价值的对象，应进入降级或废弃评估。降级和废弃不直接删除历史数据，应保留兼容和迁移说明。

**复盘反哺**：定期复盘是治理的核心机制。哪些状态假设反复被验证，哪些反证最常出现，哪些信号组合历史上有效——这些规律应从个人经验逐步沉淀为行业模板，再视复用情况评估是否升入本体层。复盘发现的结构性缺失，应进入本体变更流程，而不是各行业自行扩展。
