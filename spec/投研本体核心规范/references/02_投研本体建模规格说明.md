# 02-投研本体建模规格说明

本文件解释投研本体的建模规则。机器可校验字段、枚举、关系端点、动作输入和状态流转以 `schemas/objects.yaml`、`schemas/relations.yaml`、`schemas/actions.yaml` 为准。本文只说明 agent 在生成、优化、评测和推理时如何使用这些 schema。

## 1. 建模目标

投研本体用于把研究过程沉淀为可检索、可复盘、可验证、可反证的结构化资产。它不是观点汇总，也不是预测集合。每个概念、对象、关系、状态变量、信号和判断都应服务于一个问题：后续 agent 能否基于它还原研究范围、研究链路，并知道哪些内容可信、哪些内容仍需验证。

本体必须同时满足四个要求：

| 要求 | 含义 |
|---|---|
| 可定位 | 概念、研究对象、变量、事件、资产和来源有稳定 ID。 |
| 可追溯 | 事实、观测、信号和判断能回到来源文档或明确诊断依据。 |
| 可推理 | 变量、假设、信号、判断和资产影响之间有显式关系。 |
| 可治理 | 候选、确认、降级、阻断、废弃和复盘动作有状态和审计记录。 |

## 2. 容器元数据

每份 `base_ontology`、`optimized_ontology` 或 `ontology_bundle` 必须包含 `ontology_metadata`。元数据至少说明本体 ID、版本、父版本、创建来源、更新来源、变更原因和质量分。

质量分只用于描述当前资产状态，不得把对象数量增长等同于质量提升。本小节字段与 `schemas/ontology_bundle.yaml` 中的 `ontology_container_metadata.ontology_quality` 定义保持一致，是机器可读的权威来源。

| 分数 | 检查重点 |
|---|---|
| `coverage_score` | 研究范围内对象、变量、关系、信号、情景和资产映射是否足够。 |
| `evidence_score` | 来源、事实观测、证据等级和可追溯性是否充分。 |
| `temporal_evidence_score` | EvidenceEpisode、EvidenceClaim、有效期、失效记录和当前有效证据过滤是否充分。 |
| `patch_audit_score` | PatchRequest、PatchLedgerItem、合并/拒绝原因和版本演化审计是否充分。 |
| `consistency_score` | schema 合法性、关系端点、重复、冲突和状态一致性是否合格。 |
| `reasoning_score` | 是否支持链路推理、反证、情景路径和资产线索表达。 |

## 3. 对象分层

对象分为五层。agent 必须先判断对象属于哪一层，再决定是否新增、更新、合并、降级或拒绝。

| 层级 | 典型对象 | 建模规则 |
|---|---|---|
| 概念定义层 | `ConceptScheme`、`Concept`、`ConceptBoundary` | 描述研究范围、术语定义、同义词、纳入/排除/交叉边界和概念到业务对象的映射。 |
| 研究标的层 | `Industry`、`Segment`、`Company`、`Product`、`Material`、`Asset` | 描述真实研究对象。对象存在不代表存在业务箭头，业务连接必须由关系表达。 |
| 可观测维度层 | `Event`、`StateVariable`、`StateVariableObservation`、`StateVariablePropagation` | 描述发生了什么、观察什么、观测到什么、变量如何传导。预测不能写成观测。 |
| 研究推理层 | `StateHypothesis`、`Signal`、`JudgmentOutput`、`ScenarioPath`、`AssetImpact`、`InvestmentThesis` | 描述假设、验证、反证、判断、情景和资产影响线索。资产影响不是买卖建议。 |
| 来源与记录层 | `SourceDocument`、`EvidenceEpisode`、`EvidenceClaim`、`EvidenceFact`、`PatchRequest`、`PatchLedgerItem`、`InferenceRun`、`ActionAudit`、`ReviewRecord` | 记录来源、证据摄入、证据主张、候选事实、补丁请求、增量账本、推理运行、动作和审核。没有来源的事实必须降级或列为缺证。 |

## 4. 关键对象规则

`ConceptScheme` 表示某个行业、主题或研究范围的概念体系。它回答"本体讨论哪个概念空间"，例如半导体产业概念体系。核心规范只定义结构，具体行业概念不写死在核心规范里。

`Concept` 表示术语和范围口径，例如半导体、先进封装、光通信、硅光、光模块。每个关键概念必须说明定义、类型、当前本体范围状态、同义词或英文名，并尽量绑定权威来源。

`ConceptBoundary` 记录纳入、排除、相邻、交叉或延后的边界裁定。它用于解释为什么某概念被纳入当前本体，或为什么只作为相邻概念保留。例如光通信整体可标为 adjacent，但硅光、光芯片、DSP、CPO 等可通过 overlap 或映射关系进入半导体本体。

概念层不替代业务对象层。`Concept` 负责语言和范围，`Industry`、`Segment`、`Product`、`Material` 等负责图谱实体和业务关系。需要参与图谱或推理时，必须通过 `conceptMapsToObject` 映射到正式对象。

`Event` 只记录已发生、已披露或明确可定位的事件。行业主题、模板、长期趋势不能伪装成事件。

`StateVariable` 表示可持续观察的维度，例如价格、库存、产能、良率、订单、政策强度、竞争格局。变量必须有口径或待补口径，不能只写“景气度”“利好程度”这类不可观察词。

`StateVariableObservation` 表示某个变量在某个业务时间的读数、事实或状态。它必须区分业务时间和系统录入时间，并绑定来源。分析师预测、目标价、评级、推荐语、收益率推断和仓位表达不得作为观测。

`StateVariablePropagation` 表示变量之间的传导机制。传导必须说明方向、时滞、边界条件和证据状态；不能只用自然语言段落替代。

`Signal` 用于支持、催化、跟踪、削弱或阻断假设/判断。blocking 信号必须作用于明确对象，不能直接把新闻写成最终结论。

`JudgmentOutput` 是研究结论的结构化表达。它必须绑定假设、证据、适用范围、置信度和反证条件，不得输出买卖建议、目标价、收益率预测或仓位建议。

`AssetImpact` 只能表达资产影响线索、方向、时间窗口、定价状态和验证点。它不能替代投资建议。

`EvidenceEpisode` 表示一次材料、历史案例、推理反馈、评测反馈或结构化数据摄入。它不是正式业务对象，不能替代 `Industry`、`Company`、`Event` 等主干对象。

`EvidenceClaim` 表示从 episode 中抽取出的最小可追溯主张。它可以是事实、估算、预测、传导、信号、反证、情景或资产映射线索。`restricted_item`、`author_judgment`、`forecast` 类型不得直接写成事实观测。

`EvidenceFact` 表示由一个或多个 claim 归并出的结构化事实候选。它只能作为正式对象、观测、信号或关系的候选来源，不能绕过优化 Skill 进入正式本体。

`PatchRequest` 表示候选改动请求，可由缺口发现、历史回放、评测、推理反馈或人工修订产生。它不代表正式本体已经变化。

`PatchLedgerItem` 是本体优化 Skill 的 append-only 增量审计记录。正式合并、拒绝、延后或失败都必须留下账本项。

`InferenceRun` 记录一次推理使用的业务时间、本体版本、中心对象、证据、排除的失效证据、推理链和反馈。它是运行日志，不是正式判断或发布结论。

## 5. 关系建模

关系是图谱可用性的核心。agent 不得用对象字段、对象顺序、标题层级或 `positionInChain` 暗示关系。

| 关系类别 | 使用规则 |
|---|---|
| 概念关系 | 上位、下位、包含、交叉、排除、边界裁定和概念到对象映射必须显式建边。 |
| 业务结构关系 | 产业链、公司、产品、材料、资产、事件之间的结构连接必须显式建边。 |
| 变量挂载关系 | 变量、观测和事件要挂到适当对象或事件上，避免孤岛变量。 |
| 传导关系 | `StateVariablePropagation` 必须通过 `propagatesFrom`、`propagatesTo` 连接端点变量。 |
| 假设与信号关系 | 假设、信号、判断之间必须通过支持、跟踪、削弱、阻断等关系连接。 |
| 来源追溯关系 | 来源文档必须通过 `sourceOf` 或等价关系追溯到被支持对象、观测、信号或判断。 |
| 证据图谱关系 | Episode、Claim、Fact、Patch 和推理运行必须通过 `claimFromEpisode`、`episodeMentionsObject`、`claimSupportsObject`、`claimSupportsRelation`、`claimInvalidatesClaim`、`claimTriggersPatch` 等关系表达。 |
| 资产影响关系 | 资产影响必须从判断、假设或变量链路派生，再连接到资产。 |

常用业务结构关系：

| 关系 | 用途 |
|---|---|
| `conceptInScheme` | 表达概念属于哪个概念体系。 |
| `conceptIncludes` / `conceptExcludes` / `conceptOverlapsWith` | 表达概念纳入、排除和交叉边界。 |
| `boundaryForConcept` | 表达边界裁定作用于哪个概念。 |
| `conceptMapsToObject` | 表达概念如何映射到 Industry、Segment、Product、Material、Asset、Event 或 StateVariable。 |
| `segmentConnectsToSegment` | 表达环节之间供应、加工、组装、销售、替代、互补或竞争。 |
| `companyRelatesToCompany` | 表达供应、客户、代工、渠道、合作、竞争、投资控制或授权。 |
| `productRelatesToProduct` | 表达依赖、替代、互补、代际、部件、集成、竞争或使能。 |
| `materialUsedInProduct` | 表达材料在产品中的用途、用量角色或约束。 |
| `eventRelatesToEvent` | 表达事件链、阶段关系或因果顺序。 |
| `eventAffectsVariable` | 表达事件影响哪个变量以及影响方向。 |
| `assetExposedToTarget` | 表达资产对公司、行业、产品、材料或变量的暴露。 |
| `claimFromEpisode` | 表达 EvidenceClaim 来自哪次 EvidenceEpisode。 |
| `episodeMentionsObject` | 表达 Episode 提及了哪些本体对象或证据对象。 |
| `claimSupportsObject` | 表达 EvidenceClaim 支持哪个对象、信号、观测、判断或 PatchRequest。 |
| `claimSupportsRelation` | 表达 EvidenceClaim 支持某条关系实例或关系补丁，具体关系 ID 由属性记录。 |
| `claimInvalidatesClaim` | 表达新主张使旧主张失效、被替代或范围变化。 |
| `claimTriggersPatch` | 表达 EvidenceClaim 触发候选本体补丁。 |

## 6. 状态和证据

AI 新增或修改的内容默认是 `candidate`。只有来源充分、口径清楚、端点合法、可追溯并通过对应流程确认后，才可以升级为更高状态。

证据等级必须反映来源质量：

| 来源 | 默认处理 |
|---|---|
| 公告、财报、政策原文、交易所文件、官方数据 | 可作为高可信事实来源。 |
| 券商研报、行业数据、可追溯调研纪要 | 可作为中等可信分析和线索来源。 |
| 新闻转载、二手摘要、AI 摘要、无原文位置材料 | 只作线索，不支撑关键确认。 |
| 分析师预测、评级、目标价、推荐语 | 可记录为受限观点，不得作为事实观测。 |

缺少来源、来源弱、端点不明、口径冲突、分类不确定或疑似越界时，应降级、延后或写入 unresolved 列表，不得静默补全。

Temporal Evidence Layer 的额外规则：

- 新证据进入时先形成 `EvidenceEpisode` 和 `EvidenceClaim`，不得直接写入正式主干对象。
- 每条 claim/fact 可以记录 `validFrom`、`validTo`、`observedAt`、`learnedAt`、`invalidatedAt`、`invalidatedBy`、`supersedes` 和 `supersededBy`。
- 新事实否定旧事实时，旧事实只能标记为失效或被替代，不得物理删除。
- 推理默认只使用目标 business time 下仍有效、未被 invalidated 的证据；历史回放可以读取当时曾经有效的证据。
- `05-缺口发现 Skill` 直接从 `evidence_claims.yaml` 消费证据 claim，内部生成缺口发现视图（`_work/gap_reference_view/`），不判断本体覆盖。

## 7. 动作和审计

对对象、关系、变量、信号、判断和资产影响的关键变更必须映射到动作，并留下 `ActionAudit` 或等价审计记录。动作至少说明：动作类型、目标 ID、输入依据、状态变化、执行主体、执行时间和复核状态。

常见动作：

| 动作 | 使用场景 |
|---|---|
| create/add | 新增对象、关系、变量、观测、传导、信号或判断。 |
| update/strengthen | 补字段、补关系、补证据、增强传导或提高可验证性。 |
| split/merge | 处理变量过粗、对象重复、口径重叠或边界混乱。 |
| downgrade/deprecate | 证据不足、过期、被反证或不再适用。 |
| reject | 越界、不可验证、低价值、违反合规边界或无法映射。 |
| keep | 经检查后保留原内容，并说明保留依据。 |

Patch 相关动作遵守以下约束：

- `CreatePatchRequest` 只能创建候选改动请求。
- `AppendPatchLedgerItem` 只能由本体优化 Skill 在合并、拒绝、延后或失败时执行。
- Patch ledger 创建后不可修改；更正必须追加新的 ledger item。
- Evidence Graph 不能绕过优化 Skill 修改 `02_objects.yaml`、`03_relations.yaml`、`04_actions.yaml` 或 `05_reasoning.yaml`。

## 8. 质量门槛

一份可交给下游使用的本体应满足的质量门槛，已在《03》§6 中统一为权威的最小校验清单，涵盖 bundle 结构完整性、元数据与版本、对象与关系质量、可观测维度与推理链、证据可追溯性、Temporal Evidence Layer 合规、Patch Ledger 审计、推理运行记录、跨模块一致性和合规边界等维度。此处不重复列举，Agent 和校验脚本以《03》§6 为准。

## 9. 冲突处理

当本文件、任务 Skill 和 schema 出现冲突时，按以下顺序裁定：

1. `schemas/objects.yaml`、`schemas/relations.yaml`、`schemas/actions.yaml`
2. `references/03_本体Bundle文件契约.md`
3. `references/01_投研本体核心说明.md`
4. 本文件
5. 任务型 Skill 的 `SKILL.md`
6. 任务型 Skill 的 reference、example 和临时说明

任务型 Skill 不得自行扩展核心对象、关系、动作或公共枚举。确需扩展时，只能输出核心规范变更建议，并说明适用场景、禁止用法、迁移影响和反例。
